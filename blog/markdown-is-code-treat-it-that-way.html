Thesis May 2026

Markdown is code.
Treat it that way.

The most consequential lines in an agent system are the ones in its instruction file. They are also, almost universally, untested, unversioned, un-diffed, and edited by whoever happens to have the chat window open.

Every serious engineering organization has the same set of habits around code. Nothing ships without review. A test suite runs before merge. There is a rollback button. There is a log that says who changed what, when, and why. These are not nice-to-haves; they are the difference between a system you can operate and a system that operates you.

Now look at the file that actually governs how a production agent behaves — the instruction file, the system prompt, the markdown that says forecast at SKU-week granularity, exclude promotional periods from the baseline, flag any week where the forecast moves more than 30% against last cycle. That file is code. It is the most behaviorally significant code in the system, because it sits upstream of every decision the agent makes. And in most deployments it has none of the habits above. It is edited live, in a chat window, by whoever is closest to the problem that afternoon. No diff. No test. No second signature. No record.

We have professionalized every category of code we run — except the one that matters most.

Why this is worse than it sounds

A bug in conventional code tends to fail loudly. A bad instruction edit fails quietly. Someone widens a rule — exclude promotional periods becomes exclude promotional and holiday periods — and the change looks reasonable, ships in a sentence, and silently degrades the forecast on the eight SKUs where holiday demand was the whole signal. Nobody reviewed it because it wasn't framed as a change. It was framed as a tweak to a text file.

The blast radius is also larger. A function touches one path. An instruction edit touches every future decision the agent makes, across every workflow that reads that file. In a core workflow — demand planning, credit recalibration, trial design — the cost of a quiet regression compounds for weeks before anyone traces it back to a one-line edit nobody remembers making.

And the people making these edits are frequently not the people who would catch the regression. The instruction encodes a domain judgment — what counts as a defensible forecast, which cases are traps, where the underwriter's experience says don't trust the obvious answer. But the edit is often made by whoever is wiring up the agent, who is not the underwriter and cannot know which clause is load-bearing.

What treating it as code actually requires

The fix is not "be more careful." It is to give instruction edits the same machinery every other kind of code already has.

  • A typed diff. Not "the prompt changed" but this clause was added, this constraint was loosened, this example was removed — rendered so a non-engineer can read exactly what is different and what it will change.
  • A regression test before merge. The edit runs against the accumulated eval set — every failure the workflow has ever produced, turned into a case — and has to clear a gate before it can ship. No step forward that loses a step already gained.
  • A two-party approval. The domain expert whose judgment the instruction encodes reads the proposed change in plain language and approves or rejects it. Their signature is the merge.
  • An append-only history. Every edit, every approval, every rejection is written to a log that cannot be quietly rewritten — so six months later you can answer who changed this, when, and what evidence said it was safe.

This is exactly what GitHub did for source code, applied to the layer above the model. The point of the comparison is not branding. It is that the discipline already exists, is well understood, and has simply never been pointed at the instruction file.

The regression gate is the part people skip

Review and history are familiar. The piece that gets dropped is the test — and it is the piece that actually holds the line. An instruction edit can look like a clear improvement and still be a regression somewhere you weren't looking, because the workflow's failure modes are not all visible from the case in front of you.

So the gate runs the proposed edit against the whole accumulated eval set and returns more than a pass/fail. It distinguishes a true regression (rejected and logged), a no-improvement edit that would only bloat the eval set (rejected to keep the set honest), and a sandbox or execution error (escalated, never silently passed). In our demand-forecasting replay, every regressive proposal the loop generated was caught and rejected by the gate before it could reach the live instruction file.

The bridge

Treating markdown as code is the entry point to the whole improvement loop. Once the instruction file has a diff, a test, an approval, and a history, the obvious next questions follow on their own: where do the test cases come from, who writes the proposed edit, who signs off, and how do you prove later that nothing regressed. Those are the next posts. This is the premise they all rest on.

The instruction file is the highest-stakes code you run. Stop editing it in a chat window.
